How to use this guide

All commands run in Ubuntu (WSL), from the lab folder, while the lab is deployed. Define the container prefix once per terminal:

cd ~/projects/mini-dc-lab
P=clab-mini-dc

Every section starts with How it works (what the layer does), then a table: the command, the result you must get, and why that result proves the feature. Lines marked BLOCKED / DENIED are expected to fail — they demonstrate a security control. docker exec $P-<node> <cmd> runs a command inside that node, exactly as if you were logged into the device.

Right after a deploy, wait about 30 s for OSPF / spanning tree to converge, and 2–4 min for TrueNAS (storage01) to boot before testing the SAN. TrueNAS console: http://localhost:6080/vnc_lite.html?scale=true.

1. Internet & edge routers

How it works. Two ISPs (isp-a, isp-b) give the data center two independent Internet exits. Each edge router (FRRouting) has a static default route to its ISP and announces it into OSPF with a different cost (10 on edge-r1, 20 on edge-r2), so all traffic leaves through ISP A while it is up. The edges also do NAT: they hide internal addresses behind their WAN IP (masquerade) and publish the DMZ web servers on port 80 (port-forward / DNAT).
CommandExpected result → why it matters
docker exec $P-edge-r1 ping -c3 8.8.8.8replies → the ISP A uplink works end to end
docker exec $P-edge-r2 ping -c3 8.8.8.8replies → the backup ISP B uplink also works, ready for failover
docker exec $P-edge-r1 vtysh -c "show ip route"S>* 0.0.0.0/0 via 10.0.0.2 and O>* routes → static default to the ISP + internal networks learned by OSPF
docker exec $P-edge-r1 vtysh -c "show ip ospf neighbor"fw-01 (10.255.0.40) Full → the edge exchanges routes with the firewall
docker exec $P-edge-r1 nft list table ip natmasquerade and dnat to 10.10.60.10 → outbound NAT and the published DMZ web server

2. Firewall (fw-01) — overview

How it works. fw-01 replaces pfSense: FRRouting for OSPF + nftables for the security policy. It has three zones: outside (eth1/eth2 → edges), inside (eth3/eth4 → cores) and the DMZ (eth5). The forward chain has a default-drop policy: only the flows listed are allowed — inside → anywhere, Internet → DMZ web (80/443, ping), DMZ → MariaDB (db01:3306) and DNS (dns01:53), DMZ → Internet (80/443/53). Everything else is counted and logged as FW-01 DROP. Replies to allowed connections pass thanks to connection tracking (ct state established,related accept).
CommandExpected result → why it matters
docker exec $P-fw-01 vtysh -c "show ip ospf neighbor"4 neighbors Full → edge-r1, edge-r2, core-01, core-02: the firewall is the routing hub between zones
docker exec $P-fw-01 vtysh -c "show ip route 0.0.0.0/0"default via 10.0.1.1 (edge-r1) → the primary ISP wins (lower OSPF cost)
docker exec $P-fw-01 nft list rulesetinput + forward chains, policy drop → the complete security policy
docker exec $P-web-dmz01 curl -s -m3 http://10.10.20.10BLOCKED (no output) → DMZ → internal web is not in the allow list
docker exec $P-fw-01 nft list chain inet filter forward | tail -3FW-01 DROP counter increased → the blocked attempt was counted and logged

3. Testing the firewall rules from the firewall shell

How it works. The policy lives in the forward chain, so it filters traffic passing through the firewall — packets the firewall sends itself are not filtered. The firewall shell is therefore where you watch the rules act (counters, packet trace, connection table, captures) while a host on each side generates traffic. Use two terminals.

TERMINAL 1The firewall shell

docker exec -it clab-mini-dc-fw-01 sh

fw-01 interfaces: eth1/eth2 = outside (edges) · eth3/eth4 = inside (cores) · eth5 = DMZ · eth0 = management.

Command (inside the firewall)What it does
nft list rulesetfull policy: input chain (traffic to the firewall) + forward chain (traffic through it)
nft -a list chain inet filter forwardforward rules with their handle numbers — counters on handle 19 (Internet → DMZ web), 24 (DMZ → MariaDB) and 33 (FW-01 DROP)
nft list chain inet filter inputwho may reach the firewall itself: OSPF, ping, SSH only from the management network
nft reset counters table inet filterreset all counters to 0 before a demo
watch -n1 "nft list chain inet filter forward | grep counter"counters refreshed every second (Ctrl+C stops the watch only)
conntrack -Elive list of every new connection the firewall lets through
tcpdump -ni eth5capture everything entering / leaving the DMZ (tcpdump -ni eth5 port 3306 = only DMZ → MariaDB)

Trace one packet through the rules — shows exactly which rule decides. It adds a temporary debug chain; always remove it at the end:

nft add chain inet filter trace_in '{ type filter hook prerouting priority -301; }'
nft add rule inet filter trace_in ip saddr 10.10.60.10 meta nftrace set 1   # from web-dmz01
nft monitor trace                     # now send traffic from terminal 2 (Ctrl+C to stop)
nft delete chain inet filter trace_in # clean up

A blocked packet ends on log prefix "FW-01 DROP: "; an allowed packet shows verdict accept.

4. Core switches (Arista cEOS)

How it works. core-01 and core-02 are the layer-3 heart of the data center. They route between VLANs, and they provide a redundant default gateway with VRRP (HSRP equivalent): the virtual address .1 of each VLAN lives on core-01 (priority 110) and moves to core-02 if core-01 fails. The two cores are joined by an LACP Port-Channel (2 links seen as one), run MSTP spanning tree with core-01 as root (no loops on the redundant cabling) and OSPF with the firewall.
CommandExpected result → why it matters
docker exec $P-core-01 Cli -p 15 -c "show vlan"VLANs 20, 40, 50, 70, 99 → servers, backup, users, NOC, core transit are defined
docker exec $P-core-01 Cli -p 15 -c "show vrrp brief"core-01 Master of the 4 gateways → it currently answers on every .1
docker exec $P-core-02 Cli -p 15 -c "show vrrp brief"core-02 Backup → ready to take over in ≈3 s
docker exec $P-core-01 Cli -p 15 -c "show port-channel dense"Po1(U) with Et1 + Et2 → both inter-core links bundled: double bandwidth, survives one cable cut
docker exec $P-core-01 Cli -p 15 -c "show spanning-tree root"MST0 root, priority 4096, root port None → core-01 is the root, so the spanning tree is predictable
docker exec $P-core-01 Cli -p 15 -c "show ip ospf neighbor"fw-01 and core-02 FULL → dynamic routing to the firewall + VLAN 99 backup path
docker exec $P-core-01 Cli -p 15 -c "show ip route"O E1 0.0.0.0/0 → the default route comes from the firewall via OSPF
docker exec $P-core-01 Cli -p 15 -c "show interfaces status"all ports connected → every cable of the design is up

Interactive login, like on real hardware: ssh admin@clab-mini-dc-core-01 (password admin).

5. Top-of-Rack switches

How it works. Each rack has a ToR switch (layer 2) where the servers plug in. Every ToR is dual-homed — one uplink to each core — so a core failure does not cut the rack off. Spanning tree keeps one uplink forwarding and the other in standby (alternate) to avoid a loop. The two ToRs are also linked by an LACP bundle.
CommandExpected result → why it matters
docker exec $P-tor-01 Cli -p 15 -c "show interfaces status"uplinks + server ports connected → web01, app01, dns01 are cabled
docker exec $P-tor-01 Cli -p 15 -c "show mac address-table"MACs on Et5–Et7 → the switch learned the servers behind its ports
docker exec $P-tor-01 Cli -p 15 -c "show spanning-tree"Et1 root/forwarding, Et2 alternate → redundancy without a loop; Et2 takes over if Et1 fails
docker exec $P-tor-02 Cli -p 15 -c "show port-channel dense"Po1(U) Et3 + Et4 → ToR-to-ToR LACP bundle is up

6. Servers & connectivity

How it works. Servers sit in VLAN 20 (10.10.20.0/24) and use the VRRP virtual address 10.10.20.1 as their gateway — they never need to know which core is active. Traffic to another rack stays at layer 2 through the ToRs; traffic to the Internet goes core → firewall → edge → ISP.
CommandExpected result → why it matters
docker exec $P-web01 ping -c3 10.10.20.1replies → the server reaches its redundant gateway (VRRP VIP)
docker exec $P-web01 ping -c3 10.10.20.30replies → db01 in rack B is reachable across the ToRs
docker exec $P-web01 traceroute -n 8.8.8.8core → firewall → edge → ISP hops → the real path out of the data center
docker exec $P-web01 curl -s https://example.com | head -5HTML page → servers get Internet access (inside → anywhere is allowed)
docker exec $P-pc-01 curl -s http://10.10.20.10<title>web01 → a user in VLAN 50 opens the intranet

9. Security controls (must be blocked)

How it works. Defense in depth: the firewall stops the DMZ from pivoting inside; db01 runs its own host firewall (nftables) that only accepts MariaDB from the app servers and the DMZ — so users are blocked even though cEOS-lab does not enforce the core's user ACL; and the storage VLAN has no gateway at all.
CommandExpected result → why it matters
docker exec $P-web-dmz01 curl -s -m3 http://10.10.20.10 || echo BLOCKEDBLOCKED → a compromised DMZ server cannot pivot inside
docker exec $P-pc-01 nc -z -w2 10.10.20.30 3306 || echo BLOCKEDBLOCKED → users cannot reach the database (db01 host firewall)
docker exec $P-web01 ping -c2 -W1 10.10.30.10 || echo BLOCKEDBLOCKED → the SAN (VLAN 30) is not routed
docker exec $P-db01 nft list rulesetaccept 3306 from app/DMZ only → the host firewall rules

10. SAN – TrueNAS SCALE iSCSI storage

How it works. storage01 runs TrueNAS SCALE 25.10 as a KVM virtual machine. Its two data disks form a ZFS mirror pool tank (survives a disk failure). Each server gets its own block volume (zvol) exported as an iSCSI LUN: tank/db (10 GiB) for db01, tank/backup (4 GiB) for backup01. Each target accepts logins only from its server's storage IP. Servers use dedicated storage NICs on VLAN 30, which has no gateway.
CommandExpected result → why it matters
docker exec $P-storage01 pgrep -a qemu-systemqemu with accel=kvm → the TrueNAS VM runs with hardware virtualization
docker exec $P-db01 ping -c2 10.10.30.10replies → db01 reaches TrueNAS on its storage NIC
docker exec $P-db01 iscsi-ls -s iscsi://10.10.30.10only storage01.db, LUN 1 → db01 discovers just its own target
docker exec $P-db01 iscsi-readcapacity16 iscsi://10.10.30.10/iqn.2026-09.lab.dc:storage01.db/1last LBA 20971519 × 512 B = 10 GiB → db01 can use its disk
docker exec $P-backup01 iscsi-readcapacity16 iscsi://10.10.30.10/iqn.2026-09.lab.dc:storage01.backup/1last LBA 8388607 = 4 GiB → backup01 can use its disk
docker exec $P-db01 iscsi-readcapacity16 iscsi://10.10.30.10/iqn.2026-09.lab.dc:storage01.backup/1 || echo DENIEDDENIED ("Target not found") → a server cannot open another server's disk

13. Failover demonstrations

How it works. ./scripts/tests.sh failover breaks two things on purpose and measures the impact with a fast ping (5 per second):
ISP failover — the ISP A link of edge-r1 is cut. edge-r1 loses its default route, so OSPF withdraws it; fw-01 switches to the default from edge-r2 (cost 20) within about one OSPF dead interval. Then the link is restored and traffic returns to ISP A.
Core failover — core-01's VLAN 20 interface (the VRRP master) is shut. core-02 stops hearing VRRP advertisements and becomes Master of 10.10.20.1; servers keep the same gateway address. When core-01 comes back it preempts (priority 110) and becomes Master again.
CommandExpected result → why it matters
./scripts/tests.sh20 passed, 0 failed → the whole design works (section 12)
./scripts/tests.sh failoverISP ≈ 0.2 s, VRRP ≈ 2.8 s of loss → redundancy works; the numbers are the failover times (links are restored automatically)

Live version for a presentation — use two terminals:

# Terminal 1: continuous ping to the Internet
docker exec clab-mini-dc-web01 ping 8.8.8.8

# Terminal 2: cut ISP A, watch the pings continue through ISP B, then restore
docker exec clab-mini-dc-edge-r1 ip link set eth1 down
docker exec clab-mini-dc-fw-01 vtysh -c "show ip route 0.0.0.0/0"     # now via edge-r2 (10.0.1.5)
docker exec clab-mini-dc-edge-r1 ip link set eth1 up

Measured results: ISP failover ≈ 0.2 s (1 lost ping) · core gateway failover (VRRP) ≈ 2.8 s.

Database failover (MariaDB high availability)

How it works. db01 (primary, rack B) replicates every change live to db02 (replica, rack A) with MariaDB GTID replication. Both run keepalived (VRRP group 35), which owns the database virtual IP 10.10.20.35 (db.dc.lab) — the address all clients use — and checks MariaDB every second (mariadb-admin ping). If MariaDB on the primary dies, its health check fails and it gives up the address at once; if the whole server dies, db02 notices that the VRRP heartbeats stopped (3 × 1 s). db02 then takes the virtual IP and db-promote.sh stops replication and makes it writable. There is no automatic failback (nopreempt): restore rebuilds the failed node as the new replica.
CommandExpected result → why it matters
./scripts/db-failover.sh statusVIP owned by db01 · db02 Slave_IO/SQL_Running: Yes, 0 s behind → redundant and in sync
./scripts/db-failover.shMariaDB on the primary crashes → unavailable ≈ 2.3 s → db02 promoted, last acknowledged write present
./scripts/db-failover.sh restorethe failed node becomes the replica of the new primary → redundancy is back
./scripts/db-failover.sh serverthe primary server goes offline → unavailable ≈ 3.8 s → detected by missing VRRP heartbeats

How the time is measured: app01 writes one row through db.dc.lab every 0.2 s (new connection each time, 1 s timeout). The outage runs from the failure to the first successful write on the new primary, so it includes the promotion — not just the address move. Measured on the lab (21 Oct 2026):
